# Provably-Fair Random Winner Selector

A simple, auditable way to draw **N random winners** from a fixed list of entrants,
where **anyone** — not just the operator — can verify the result was not rigged.

The randomness comes from a **future Bitcoin block hash**: a value nobody can predict
or control at the time the draw is announced. Combined with a public commitment to the
entrant list and a fully deterministic selection algorithm, this lets any third party
reproduce the exact winners from public data.

> ### The draws
> **[DRAWS.md](DRAWS.md)** — every draw this repo has run, with its winners.
>
> Each one lives in its own folder under [`draws/`](draws/), holding two pages:
> **COMMITMENT.md** (the entrants, the number of winners and the target Bitcoin block,
> published *before* that block existed) and **RESULT.md** (the winners, with every input
> needed to check them). All of it is generated by the script, never hand-written, and
> anyone can re-check any draw with `node select.js verify`.
>
> `select.js` is the reference implementation: no dependencies, Node 18+, and the same
> code path runs the draw and verifies it.

---

## What this actually does

You want to give 3 prizes to random players, and you want people to believe it wasn't
rigged. So instead of picking the winners yourself:

1. You publish the list of eligible players **first**, and say *"the winners will be
   decided by Bitcoin block number 900030."*
2. That block doesn't exist yet. Bitcoin publishes a new one every ~10 minutes, and each
   one gets a long random ID that nobody can predict or choose — not you, not anyone.
3. When the block appears, the script turns its ID into the winners using fixed maths.

Because you promised the list and the block *before* the block existed, you couldn't have
steered the result. And because the maths is fixed and public, anyone can repeat it and
get the same three names. That's what "provably fair" means here.

## Running a draw

A step-by-step guide for the operator. No technical knowledge needed — you copy and paste
commands, and the script does the rest. Everything happens in a terminal, inside this
folder.

### Step 1 — Put the leaderboard in place

Save your leaderboard export over the existing file, so it replaces it:

```
leaderboard-export.csv
```

It needs a `Rank` column and a `player` column. A `score` column is fine, it's ignored.
Then run this line to prepare it:

```bash
node select.js convert --entrants leaderboard-export.csv --out entrants.json --rank-range 11-50 --force
```

`--rank-range 11-50` means *ranks 11 to 50 are eligible*. Change those numbers if the
prize rules change.

You'll see it list the players it kept. Check the count looks right.

### Step 2 — Lock in the list

```bash
node select.js commit --rank-range 11-50 --n 3 --ahead 20
```

`--n 3` is how many winners. `--ahead 20` means the deciding block is about 3.5 hours away.

This prints a **commitment hash** (a long code that acts as a fingerprint of your exact
player list) and a **block number**. It creates a new folder like
`draws/2026-09-09T142351Z-block900030/` — the UTC time it was committed, plus the
block that will decide it.

Now publish it:

```bash
git add -A
git commit -m "Commit: draw parameters + entrant list"
git push
```

### Step 3 — Announce it publicly

**This step is not optional.** It's what proves you committed before the result was
knowable. Post in your Discord, or wherever your players are:

> **3 random prizes for ranks 11–50.**
> The winners will be decided by **Bitcoin block 900030**, which hasn't been mined yet —
> so nobody knows them yet, us included.
> The full list of eligible players is already published here: https://github.com/cloudbet/provably-fair-tournament-winner-picker/blob/main/draws/…/COMMITMENT.md
> Once that block appears we run the draw and post the winners, and you can check them
> yourself.

Use the real block number the script printed. For the link, take the folder name it
printed and paste it into this address:

```
https://github.com/cloudbet/provably-fair-tournament-winner-picker/blob/main/draws/FOLDER-NAME/COMMITMENT.md
```

### Step 4 — Wait

About 3.5 hours. Step 2 printed a mempool.space link — that page shows the block once it
exists.

### Step 5 — Run the draw

```bash
node select.js draw
```

Three names appear. That's the result. You have no say in it, and running it again can't
change it.

Publish it:

```bash
git add -A
git commit -m "Result: winners drawn"
git push
```

Then announce:

> **Winners:** [name], [name], [name]
> Decided by Bitcoin block 900030. Full result and every input:
> https://github.com/cloudbet/provably-fair-tournament-winner-picker/blob/main/draws/FOLDER-NAME/RESULT.md
> Don't trust us — check it yourself:
> `git clone https://github.com/cloudbet/provably-fair-tournament-winner-picker.git && cd provably-fair-tournament-winner-picker && node select.js verify`

Done.

## The next tournament

Exactly the same five steps. Replace the contents of `leaderboard-export.csv` with the new
leaderboard and start again from Step 1.

**Nothing from the last tournament is affected.** Each draw gets its own folder with its
own copy of its player list, so old results stay published and stay checkable forever.
`DRAWS.md` just gains a row.

---

## Three rules

1. **Announce before the block.** Steps 2 and 3 have to happen before that block is mined.
   That's the whole point.
2. **Don't edit a draw's folder once it's pushed.** `draws/<this-draw>/` holds the
   snapshot every check runs against. The script will catch an edit there and it will look
   like cheating even if it wasn't. The leaderboard and `entrants.json` at the repo root
   are working files — replacing them for the next tournament is expected and affects no
   existing draw.
3. **Don't run the draw twice.** It refuses by default. Forcing it would look like
   re-rolling until you liked the winners.

## If something goes wrong

| What you see | What it means |
|---|---|
| `could not read the Bitcoin tip height` | No internet. Connect and try again. |
| `block 900030 is not mined yet` | Too early. Wait — it tells you how many blocks to go. |
| `target block 900030 already exists` | The block you picked has already happened. Use a bigger `--ahead`. |
| `result.json already exists` | This draw is already done. Look in its folder. |
| `more than one draw is waiting` | You started two draws. It lists them — add `--draw <folder>` to pick one. |
| `cannot tell which field is the entrant identifier` | The CSV columns aren't recognised. Rename the player column to `player`. |
| `lists the same entrant more than once` | Two identical player names in the CSV. Fix the spreadsheet. |
| `FAIL` from verify | Something changed after the commitment. Read which line failed. |

Nothing here can quietly go wrong: every command either works or stops with an
explanation, and it never overwrites a published draw.

## Want to test it first?

You can rehearse the whole thing without waiting hours. Use `--ahead 2` in Step 2, wait
~20 minutes, then run Step 5. It will warn you that 2 blocks is very little margin —
that's expected for a rehearsal, and fine. Delete the practice folder from `draws/`
afterwards and don't push it.

To check the maths itself at any time, with no internet and no files touched:

```bash
node select.js selftest
```

It runs 12 checks and prints `PASS`.
